# Talk track: Cedar in Privilege

One-liner: "Cedar is the rule engine inside the Privilege gateway: it can refuse a call, hold it for a human, or let it through. Here are three cases, simulated, and one of them measured on a real tenant."

## The walk (about 8 minutes)

1. **Point at the banner.** The runs are simulated: a mock token and a mock door. The door evaluates three rule shapes, it is not a Cedar engine, and it decides nothing real. Only the act.sub case has a result measured on a real tenant. (15 seconds.)
2. **Case 1, hold for a human.** Run "Hold: no approval yet". A forbid on mcp:InvokeUnattended with an unless approval_count >= 1 holds the call: it is not refused, it waits, and the door hands back an approval id. Then run "Hold, approve, retry": a person approves, the retry goes through. This shape is console text from the full demo app's notes (not re-run here), and the hold itself is simulated; its real counterpart is the Privilege AI Policies page of the full demo app.
3. **Case 2, token-scope gate.** Run "Token without the scope": the policy wants a scope the token does not carry, so the call is refused with JSON-RPC -32600 and the reason names the scope. Run "Token with the scope": same policy, same tool, served. Simulated; the shape is console text. Whether a PingFederate token's scope reaches the policy was not tested (UNVERIFIED). Its real counterpart is the PingFederate Token Demo page of the full demo app.
4. **Case 3, agent act.sub gate.** Run "Two policies, same token". CountTool is allowed (its policy names this agent), ListIndexTool is refused (its policy names a different value): `action denied by policy: ListIndexTool requires act.sub to be agent-b-example`. Open "What the mock door did (simulated)" to show the two checks the mock computed. This is the case with a measured counterpart.
5. **Candidate.** Run "Candidate state". Per the console documentation (not re-run here, UNVERIFIED) a Candidate is stored and checked but not enforced, so always start there and move to Active when you are happy.
6. **Ask the agent.** Pick "Two policies, same token" and press Send on the suggested prompt, or type your own ("how many entries are there?"). The agent is scripted, not a model: it reads count, list or search and, for overnight or unattended, runs the call with nobody watching. Walk the conversation, then the API calls: the token request to the mock PingFederate, then each `tools/call` and the door's reply. The policy decides, not the prompt: ask it to ignore the policy and it is still refused or held. For a hold, play the approver and watch the agent retry. All simulated.
7. **Scroll to Set up Cedar in Privilege.** Walk the eight console steps: sign in, Access Management, AI Policies, New Policy, name it and pick Candidate, pick a template, read the "Cedar this will save" preview, Create Policy and read Validation & Stages, then Enforce, wait and test. Every line is labelled console text, measured or UNVERIFIED.
8. **Is and Is not.** Cedar is a per-call rule engine that can narrow, with three actions; console text says it is not authentication, not instant and not everything; it is believed not to be a grant, not the RequiredClaims gate and not a regex engine (UNVERIFIED, not tested here). Say which lines are UNVERIFIED.
9. **Scroll to the Measured card.** This part is not a mock run: it is what happened on a real tenant on 2026-11-16, for the act.sub case only. In one run the first poll, about 7 seconds after the policies were created, already showed the refusal. That is one observation, not a measured or guaranteed propagation time. Read the "Not measured" list aloud.

## If asked

- **"Is the agent a real model?"** No. It is a small scripted planner that reads count, list, search and overnight, so every run is the same and nothing leaves the machine. What is real about the demo is the shape: the agent calls the door with a token, and the door's policy answers.
- **"Is this a real Cedar engine?"** No. The mock evaluates three rule shapes. The Cedar text shown is generated by this lab from each shape, with example ids. For act.sub only the `contains(...)` test inside `forbid ... unless` was read from the real tenant; every other line is UNVERIFIED against it.
- **"Was the hold case run for real?"** Not in this lab. It is simulated here. The full demo app's notes record a live hold on a real door; this lab did not re-run it.
- **"Did you test two different agents?"** Not for real. The one real client always carried a single act.sub; the refusal came from a policy naming a different value.
- **"Is there a simpler way than a policy?"** RequiredClaims on the identity or grant is believed to do the same job earlier, at sign-in. UNVERIFIED: not tested here.
- **"Can it match a pattern, or a part of the value?"** The act.sub template's rule is a `.contains()` test on the claim, not a pattern. The mock compares exactly; whether the real rule is exact, substring or set membership was not measured (UNVERIFIED).
- **"Why did my policy not refuse anything?"** Check its state first: per the console documentation (not re-run here, UNVERIFIED) a Candidate is not enforced, only Active is. Then remember a change can take about 4 minutes to reach the gateway per the documentation; one observation on a real tenant showed 7 seconds (one observation, not a propagation time).
- **"Is Real mode in the page?"** Owner-gated: with a valid local `.env`, Real runs the same read-only probe `npm run real` runs (the act.sub case; the server never calls out without it), labelled REAL on the page. The hold and scope cases stay simulated; the hold/scope live counterparts are pages of the full demo app. The measured table came from the 2026-11-16 run of the probe shape against a real PingFederate and door.
